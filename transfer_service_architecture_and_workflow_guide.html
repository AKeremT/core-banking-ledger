TransferService Derinlemesine Çalışma Rehberi

Para transferi sıradan bir CRUD işlemi değildir. Ağ gecikmelerine, eşzamanlı veri yarışlarına (Race Condition) ve çift harcamalara (Double Spending) karşı inşa ettiğimiz 5 Güvenlik Kapısı ve defter mekanizması.

🧭 Büyük Resim: Transfer Akışının 5 Güvenlik Kapısı (Pipeline)

İstemciden (Mobil Uygulama / API) gelen bir transfer talebi veritabanına ulaşmadan önce sırayla şu 5 istasyondan geçer:

1
İkiz İstek Zırhı
Idempotency Key kontrolü. Aynı anahtarla daha önce işlem yapıldıysa aynısını dön, paraya dokunma!
2
Deadlock Koruması
Hesap numaraları alfabetik sıralanır (Natural Order). Küçük hesap önce kilitlenir. Kilitlenme imkansızlaşır.
3
Domain Kuralları
Hesaplar ACTIVE mi? Para birimleri (Currency) eşit mi? Gönderenin bakiyesi yeterli mi?
4
Bakiye Değişimi
Gönderenin bakiyesi düşer (-), alıcının bakiyesi artar (+). Hibernate Dirty Checking bellekte hazırlar.
5
Çift Taraflı Defter
1 Transaction + 2 LedgerEntry (1 DEBIT, 1 CREDIT). Atomik olarak kaydedilir. ΣBorç = ΣAlacak.
Altın İlke: Bu 5 kapıdan herhangi birinde hata alınırsa Spring'in @Transactional(rollbackFor = Exception.class) yöneticisi araya girer; bellekteki bakiye değişimleri, açılan kilitler ve defter satırları sıfır kalıntı bırakarak veritabanından tamamen geri alınır (Rollback).

⚙️ Mekanizma ve Gerçek Hayat Senaryosu

Neden Şart? Kullanıcı metroda transfer butonuna bastı. Para düştü ama tam o anda baz istasyonu koptu. İstemci "Timeout" aldı ve 1 saniye sonra isteği tekrar attı.

  • Idempotency olmasa: Kullanıcıdan 2 kez para kesilir (Felaket!).
  • Idempotency sayesinde: Sistem ilk işlemi tanır, sıfır yan etkiyle (Zero Side-Effects) ilk işlemin dekontunu anında döner.
Kapı 2 Self-Transfer Kontrolü & Deadlock-Free Lock Ordering
TransferService.java Java 21 
if (request.senderAccountNumber().equals(request.receiverAccountNumber()))
    throw new SelfTransferException("Sender and receiver accounts are the same!");

boolean isSenderFirst = request.senderAccountNumber().compareTo(request.receiverAccountNumber()) < 0;

String firstAccountNumber = isSenderFirst ? request.senderAccountNumber() : request.receiverAccountNumber();
String secondAccountNumber = isSenderFirst ? request.receiverAccountNumber() : request.senderAccountNumber();

Account firstAccount = accountRepository.findByAccountNumberWithLock(firstAccountNumber)
        .orElseThrow(() -> new AccountNotFoundException("Account not found: " + firstAccountNumber));

Account secondAccount = accountRepository.findByAccountNumberWithLock(secondAccountNumber)
        .orElseThrow(() -> new AccountNotFoundException("Account not found: " + secondAccountNumber));

Account sender = isSenderFirst ? firstAccount : secondAccount;
Account receiver = isSenderFirst ? secondAccount : firstAccount;
💻 Kod Ne Yapıyor?
  • Gönderen ile alıcı aynıysa anında SelfTransferException fırlatır.
  • compareTo metodu ile hesap numaralarını alfabetik olarak kıyaslar (Örn: "TR100" < "TR200").
  • Kimin gönderen kimin alan olduğuna bakılmaksızın daima alfabetik olarak küçük olan hesap önce kilitlenir, büyük olan sonra kilitlenir.
  • Kilitler alındıktan sonra sender ve receiver değişkenleri asıl rollerine göre atanır.
⚙️ Deadlock Nasıl Çözüldü? (Coffman Kuralları)
Thread 1: A → B Transferi
1. Hesap A'yı kilitledi
2. Hesap B'yi bekliyor...
VS
Thread 2: B → A Transferi
1. Hesap B'yi kilitledi
2. Hesap A'yı bekliyor...

Eğer gönderen sırasıyla kilitleseydik yukarıdaki gibi Deadlock oluşur ve PostgreSQL işlemi iptal ederdi!

Bizim Çözümümüz (Natural Ordering): İki thread de alfabetik sıraladığı için (A < B), ikisi de önce A'yı kilitlemeye çalışır. Thread 1 A'yı aldığında, Thread 2 B'yi kapamaz; efendice A'nın kilidinin bırakılmasını kuyrukta bekler. Kilitlenme %100 önlenir!

💻 Kod Ne Yapıyor?
  • Gönderen veya alan hesaptan herhangi biri SUSPENDED veya CLOSED ise işlemi durdurur.
  • Hesapların para birimlerinin aynı olduğunu doğrular (Örn: TRY → USD transferini engeller).
  • BigDecimal.compareTo ile gönderenin bakiyesinin transfer tutarından büyük veya eşit olduğunu denetler.
⚙️ Neden `compareTo`? Neden `equals` Değil?

BigDecimal'da new BigDecimal("10.0") ile new BigDecimal("10.00") değerleri matematiksel olarak aynıdır ancak equals() çağrıldığında scale (ondalık hane) farkından ötürü false döner!

Sayısal büyüklük karşılaştırmasında daima compareTo kullanılmalıdır:

  • a.compareTo(b) < 0 → a küçüktür b
  • a.compareTo(b) == 0 → a eşittir b
  • a.compareTo(b) > 0 → a büyüktür b

💻 Neden `accountRepository.save(sender)` Yazmadık?

Çok kritik bir JPA sorusu: Burada accountRepository.save() çağırmadık, peki veritabanı nasıl güncelleniyor?

Cevap: Hibernate Automatic Dirty Checking!

Transaction içinde findByAccountNumberWithLock ile çektiğimiz entity'ler Hibernate'in Persistence Context'inde (Yönetilen Nesne Havuzu) yer alır. Metot biterken Hibernate nesnelerin değiştiğini otomatik fark eder ve veritabanına kendisi UPDATE accounts SET balance = ... sorgularını basar.

⚙️ Veritabanı CHECK Constraint Güvencesi

Java seviyesinde balance.compareTo(amount) >= 0 kontrolü yaptık. Peki ya kodda bir bug olursa?

Biz daha önce [`Account.java`](file:///C:/Users/AKT/Desktop/backend/core-banking-ledger/src/main/java/com/akt/banking_v1/model/Account.java) entity'sine veritabanı seviyesinde şu kuralı koymuştuk:

@CheckConstraint(constraint = "balance >= 0")

Eğer bakiye -0.01 bile olsa PostgreSQL işlemi anında iptal eder (Defense-in-Depth / Çift Katmanlı Koruma).

Kapı 5 Çift Taraflı Muhasebe (Double-Entry Bookkeeping) & Dekont
TransferService.java Java 21 
String referenceNumber = "TXN-"
        + LocalDate.now().format(DateTimeFormatter.BASIC_ISO_DATE)
        + "-"
        + UUID.randomUUID().toString().substring(0, 8).toUpperCase();

Transaction transaction = Transaction.builder()
        .idempotencyKey(idempotencyKey)
        .referenceNumber(referenceNumber)
        .type(TransactionType.INTERNAL_TRANSFER)
        .status(TransactionStatus.COMPLETED)
        .amount(request.amount())
        .currency(sender.getCurrency())
        .description(request.description())
        .build();

LedgerEntry debitEntry = LedgerEntry.builder()
        .account(sender)          // Gönderen hesaba
        .entryType(EntryType.DEBIT) // BORÇ (DEBIT)
        .amount(request.amount())
        .transaction(transaction)
        .build();

LedgerEntry creditEntry = LedgerEntry.builder()
        .account(receiver)        // Alıcı hesaba
        .entryType(EntryType.CREDIT) // ALACAK (CREDIT)
        .amount(request.amount())
        .transaction(transaction)
        .build();

transaction.getLedgerEntries().add(debitEntry);
transaction.getLedgerEntries().add(creditEntry);

Transaction savedTransaction = transactionRepository.save(transaction);
return transferMapper.toResponse(savedTransaction);
💻 Kod Ne Yapıyor?
  • Bankacılık dekont takibi için standart bir referenceNumber üretir (Örn: TXN-20261029-A7C89F12).
  • 1 adet ana Transaction kaydı oluşturur.
  • Bu transfere bağlı 2 adet defter satırı üretir:
    • Gönderen hesaba DEBIT (Borç)
    • Alıcı hesaba CREDIT (Alacak)
  • transaction.getLedgerEntries().add(...) ile ilişkilendirir.
  • transactionRepository.save(transaction) dediğimizde CascadeType.ALL sayesinde defter kayıtları da otomatik kaydedilir.
⚙️ Neden Defter Satırları (LedgerEntry) Vardır?

Sadece balance alanını güncelleseydik banka müfettişleri denetime geldiğinde:

"Bu hesaptan 500 TL çıkmış ama paranın nereye gittiğine dair hiçbir hukuki ispatınız yok!" derdi.

Değişmez Defter İlkesi (Immutability):

  • Defter kayıtları silinemez ve güncellenemez (updatable = false).
  • Her transferin borç ve alacak toplamı birbirine eşittir: Σ DEBIT == Σ CREDIT.
  • Yıllar sonra bile her kuruşun nereden nereye aktığı matematiksel olarak ispatlanabilir.
🧠 Özel Bölüm: Neden `accountRepository.save(sender)` Yazmadık? (Kütüphaneci & Snapshot Analojisi)

Yazılıma yeni başlayanların en sık kafasını karıştıran ve mülakatlarda kıdemli geliştiricileri hemen ele veren soru şudur:
sender.setBalance(newBalance); yazdık, peki veritabanı nasıl güncelleniyor da biz accountRepository.save(sender) çağırmadık?

📖 Senaryo 1: Raftan Çekilen Defter (`Account sender`) → save() GEREKSİZ!

1. Kodun başında accountRepository.findByAccountNumberWithLock("TR100") dediniz.

2. Kütüphaneci (Hibernate) gitti, raftan orijinal defteri aldı ve masanıza açık şekilde koydu.

3. Defteri masaya koyduğu an, sayfanın gizlice polaroid fotoğrafını (Snapshot) çekti: (Bakiye: 1.000 TL).

4. Siz masadaki açık defterin üstünü çizip 700 TL yazdınız (sender.setBalance(...)).

5. Metot bitti (@Transactional kapandı). Kütüphaneci defteri rafa geri koymadan önce polaroid fotoğrafa baktı:

"Dur bir dakika! Masaya koyduğumda 1.000 TL'ydi, şimdi 700 TL olmuş. Bu sayfa DEĞİŞMİŞ (DIRTY)!"

→ Kütüphaneci siz tek kelime etmeseniz bile, otomatik olarak rafa gidip UPDATE accounts SET balance = 700... yazar!

📄 Senaryo 2: Masada Sıfırdan Üretilen Fiş (`Transaction`) → save() ŞART!

1. Masada boş bir kağıt aldınız ve sıfırdan bir transfer fişi yazdınız: Transaction.builder()...build().

2. Bu fiş kütüphanenin rafında henüz hiç yok.

3. Kütüphaneci masanızda sıfırdan karaladığınız bu yeni kağıttan tamamen habersizdir (Snapshot'ı yoktur).

4. Metot biterken kütüphaneci "Bu kağıt da neyin nesi?" diyemez çünkü onunla hiçbir bağı yoktur.

→ O yüzden kütüphaneciye gidip açıkça teslim etmek zorundasınız:

transactionRepository.save(transaction); // "Al bu yeni fişi rafa kaydet!"
🔄 Hibernate Automatic Dirty Checking Yaşam Döngüsü (Life-Cycle)
ADIM 1: ODAYA GİRİŞ
findByAccountNumberWithLock()
Entity Managed (Yönetilen) duruma geçer. Persistence Context'e eklenir.
ADIM 2: FOTOĞRAF (SNAPSHOT)
Snapshot Alınır
Hibernate ilk halini belleğin gizli bir köşesinde saklar: balance = 1000.
ADIM 3: SETTER İLE DEĞİŞİM
sender.setBalance(700)
Sadece Java nesnesi değişti, veritabanına henüz SQL atılmadı.
ADIM 4: OTOMATİK FLUSH
Metot Biter (Commit)
Hibernate kıyaslar: 1000 ≠ 700! Kendisi otomatik UPDATE gönderir!
Kriter Account sender (Raftan Çekilen) Transaction (Sıfırdan Üretilen)
Nesnenin Doğuşu Veritabanından findBy... ile geldi Java kodunda builder().build() ile sıfırdan doğdu
JPA / Hibernate Durumu MANAGED (Yönetilen / Takipte) TRANSIENT (Geçici / Habersiz)
Snapshot (Fotoğraf) Var mı? EVET (İlk hali hafızada) HAYIR (Hiç çekilmedi)
`save()` Çağrısı Gerekli mi? GEREKSİZ (Hibernate kendisi halleder) ŞART (Tanıtmak için zorunlu)
SQL Karşılığı Otomatik UPDATE accounts SET balance = ... INSERT INTO transactions (...)
Kıdemli Mühendis Mülakat Notu:
"Peki accountRepository.save(sender) yazsaydık kod bozulur muydu?"
Hayır, kod patlamazdı. Ama Spring Data JPA'nın save() metodu gereksiz yere bir entityInformation.isNew() ve ardından entityManager.merge() kontrolü çalıştırırdı. Kütüphanecinin önünde açık duran defteri gösterip kütüphaneciye tekrar 'Bunu kaydet' demek gibidir; kıdemli bir kod incelemecisi (code reviewer) bunu gördüğünde JPA yaşam döngüsünün tam kavranmadığını anlar!
🔑 TEK CÜMLELİK ALTIN KURAL:
Sıfırdan yarattığın nesneyi save() ile tanıtırsın; veritabanından çektiğin nesneyi ise sadece set...() ile değiştirirsin, @Transactional bitişinde Hibernate onu otomatik kaydeder!
📊 Bir Transfer Sırasında Veritabanında Neler Değişir? (Somut Örnek)

Senaryo: Hesap A (Bakiye: 1.000 TL), Hesap B'ye (Bakiye: 200 TL) 300 TL para gönderiyor.

Tablo Adı Kolonlar / Kayıtlar Transfer Öncesi (T0) Transfer Sonrası (T1) Muhasebe Mantığı
accounts (Hesap A) balance, status 1000.0000 TL 700.0000 TL Gönderen hesaptan 300 TL eksildi
accounts (Hesap B) balance, status 200.0000 TL 500.0000 TL Alıcı hesaba 300 TL eklendi
transactions type, status, amount, refNo Kayıt Yok COMPLETED | 300 TL İşlemin üst başlığı ve idempotency anahtarı mühürlendi
ledger_entries (1. Satır) account_id, entry_type, amount Kayıt Yok Hesap A | DEBIT | 300 TL Hesap A'nın borçlandığı değişmez satır
ledger_entries (2. Satır) account_id, entry_type, amount Kayıt Yok Hesap B | CREDIT | 300 TL Hesap B'nin alacaklandığı değişmez satır
Matematiksel Sağlama:
Hesap A değişimi: -300 TL | Hesap B değişimi: +300 TL
Defter Girişleri: 1 x DEBIT (300 TL) == 1 x CREDIT (300 TL) → Net Fark: 0.00 TL (Sıfır Hata)
💡 Mülakat & Kıdemli Mühendis Soru-Cevap Köşesi
❓ Soru 1: Deadlock'ı veritabanında çözmek varken neden Java katmanında çözdünüz?
Cevap: Veritabanları (PostgreSQL vb.) deadlock oluştuğunda bunu "Deadlock Detector" ile tespit edip işlemlerden birini PSQLException: deadlock detected ile iptal eder (kill eder). Bu durum istemciye hata döner ve veritabanı CPU'sunu yorar. Biz compareTo ile hesap numaralarını alfabetik sıraya sokarak Circular Wait (Döngüsel Bekleme) şartını daha kilit talep edilmeden ortadan kaldırdık. Böylece deadlock veritabanına hiç yansımaz, thread'ler birbirini sırayla bekler.
❓ Soru 2: Neden `Account.balance` güncellendikten sonra `accountRepository.save(sender)` çağırmadık?
Cevap: Spring'de @Transactional metotlar içinde JPA Persistence Context (EntityManager) aktiftir. findByAccountNumberWithLock ile çekilen entity'ler Managed (Yönetilen) durumdadır. Hibernate, metodun bitiminde (Transaction commit anında) entity üzerindeki değişiklikleri otomatik tespit eder (Dirty Checking) ve gerekli UPDATE sorgusunu veritabanına kendisi gönderir. Gereksiz save() çağrısı yapmak gereksiz flush veya kod kalabalığı yaratır.
❓ Soru 3: Neden sınıf seviyesinde `@Transactional(readOnly = true)`, metot seviyesinde `@Transactional(rollbackFor = Exception.class)` kullandık?
Cevap: Sınıf seviyesindeki readOnly = true, "Varsayılan Olarak Güvenli" (Secure by Default) mimarisidir; okuma metotlarında Hibernate'in nesne kopyası (snapshot) almasını kapatarak bellek tasarrufu sağlar. Metot seviyesindeki tanım ise bunu ezer (override). rollbackFor = Exception.class ise Spring'in varsayılanda Checked Exception'larda rollback yapmama açığını kapatır ve her türlü hatada işlemi atomik olarak geri alır.
❓ Soru 4: Idempotency tablosunda neden `idempotencyKey` kolonu UNIQUE olmak zorundadır?
Cevap: İki istek aynı anda (aynı milisaniyede) gelse bile veritabanındaki UNIQUE CONSTRAINT sayesinde aynı anahtara sahip ikinci istek DataIntegrityViolationException alır ve iki kez para çıkışı fiziksel olarak imkansız hale gelir.
