JPA'de Equals & HashCode Rehberi

Neden standart Java mantığı Hibernate ve veritabanı dünyasında patlar? Hikayeler, görsel kutular ve satır satır kod analiziyle derinlemesine kavrayın.

📖 Büyükelçilik & Posta Kutuları Hikayesi (Mental Model)

Büyük bir bankanın genel müdürlüğünde çalışan bir arşiv memuru olduğunuzu hayal edin:

1
Arşivdeki 1000 Tane Posta Kutusu (HashSet Bucket Mantığı): Müdürlükte duvar boyunca 0'dan 999'a kadar numaralandırılmış 1000 adet kilitli posta kutusu var. Bir müşterinin yeni açılan hesap evrakını arşive koyacaksınız.
2
hashCode() — Posta Kutusunun Numarasını Belirler: Evrakın üzerindeki bilgiyi bir matematiksel fonksiyona (hash) sokarsınız. Çıkan numara diyelim ki "74" oldu. Evrakı doğrudan 74 numaralı kutuya atarsınız.
3
Hızlı Arama (O(1) Karmaşıklığı): Müşteri gelip "Benim hesabım sizde kayıtlı mı?" dediğinde, 1000 kutunun hepsini tek tek gezmezsiniz! Hesabın yine hash numarasını hesaplarsınız (74). Doğrudan 74 numaralı kutuyu açarsınız.
4
equals() — Kutunun İçindeki Doğru Evrakı Seçer: 74 numaralı kutuda belki 3-4 farklı müşterinin hesabı birikmiştir. Kutunun kapağını açıp tek tek IBAN'larına bakarsınız. IBAN'ı tam uyuşan dosyayı alıp müşteriye verirsiniz.
⚠️
Büyük Facia (Kayıp Hesap Vakası): Eğer evrak kutunun içine girdikten sonra üzerindeki numara değişirse ne olur? Evrak 74 numaralı kutudadır; ama yeni numara 185 çıkmaktadır. Müşteri sorduğunda memur 185 numaralı kutuyu açar, kutu boştur! Evrak arşivde olmasına rağmen sistem "Kayıt bulunamadı!" diyerek sonsuza kadar veriyi kaybeder.

⚖️ Equals & HashCode Stratejileri Karşılaştırması

Neden JPA dünyasında geleneksel yöntemler çalışmaz? Aşağıdaki tablo tüm tuzakları özetlemektedir:

Strateji Nasıl Çalışır? JPA'deki Tehlikesi Sonuç
Varsayılan Java
Object.equals()		 Bellekteki RAM adresini kıyaslar (this == o). Veritabanından aynı hesabı 2 kez çekersen RAM adresleri farklı olduğu için Set içinde aynı hesaptan 2 tane oluşur! Kullanılamaz
Lombok
@Data veya @EqualsAndHashCode		 Sınıftaki bütün alanları (customer, entries, balance...) dahil eder. 1. customer ↔ account arasında StackOverflowError çöker.
2. Tembel yüklenen (Lazy) tabloları arkada habersizce tetikler (N+1 Sorgusu). 		Felaket
Sadece Veritabanı ID
id.equals(that.id)		 Otomatik artan birincil anahtara (PK) bakar. new Account() dediğinde id = null'dır. Veritabanına kaydedildiğinde id = 1 olur. HashSet içindeyken nesnenin Hash'i değiştiği için nesne Set içinde kaybolur! Tuzak
Business Key (Bizim Kodumuz)
accountNumber + getClass().hashCode()		 Gerçek dünyadaki benzersiz iş anahtarına (IBAN) ve sabit sınıf hash'ine bakar. 1. IBAN doğduğu andan itibaren tektir ve sabittir.
2. getClass().hashCode() asla değişmez; nesne Set içinde ömür boyu kaybolmaz. 		En İyi Pratik
💻 Account.java İçindeki Kodun Satır Satır Analizi
Account.java — equals() & hashCode() Java 21 
@Override
public boolean equals(Object o) {
    // 1. ADIM: İki değişken RAM'de zaten aynı adrese mi bakıyor?
    if (this == o) return true;

    // 2. ADIM: Karşıdaki nesne null mı veya Account değil mi?
    // (Java 16+ Pattern Matching: 'that' değişkenine otomatik cast edilir)
    if (!(o instanceof Account that)) return false;

    // 3. ADIM: Gerçek Dünyadaki IBAN (accountNumber) eşitliği kontrolü
    // that.getAccountNumber() kullanıyoruz çünkü Hibernate Proxy nesnesi olabilir!
    return accountNumber != null && accountNumber.equals(that.getAccountNumber());
}

@Override
public int hashCode() {
    // 4. ADIM: Hibernate gurusu Vlad Mihalcea standardı:
    // Nesne DB'ye gitmeden önce de, sonra da hash kodu ASLA DEĞİŞMEZ!
    return getClass().hashCode();
}
💡
Altın Kural (Getter Kullanımı): that.accountNumber yazmak yerine that.getAccountNumber() yazdık. Çünkü Hibernate bazen nesneyi tam yüklemez, yerine bir "Vekil" (Proxy) koyar. Getter çağırdığımızda vekil uyanır ve gerçek IBAN'ı getirir. Doğrudan alana erişseydik null gelebilirdi!
