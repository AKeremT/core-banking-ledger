## 2. 🏛️ Double-Entry Bookkeeping Flow

In a banking ledger, every financial transaction (`Transaction`) produces at least two immutable ledger entries (`LedgerEntry`) to maintain debit and credit equilibrium:

## 4. 🔗 Relationships & Cardinality Analysis (JPA Mapping)

### 4.1. `Customer` ⟷ `Account` (1:N)
* **Relationship Type:** A single customer can hold multiple accounts (`One-to-Many`); an account belongs strictly to one customer (`Many-to-One`).
* **Relationship Owner:** `Account` entity (`@JoinColumn(name = "customer_id", nullable = false)`).
* **Inverse Side:** `Customer.accounts` collection (`@OneToMany(mappedBy = "customer")`).
* **Fetch Strategy:** `FetchType.LAZY` on `Account` (avoids N+1 query overhead and prevents unnecessary database loading).

### 4.2. `Account` ⟷ `LedgerEntry` (1:N)
* **Relationship Type:** An account may accumulate thousands of ledger entries (`One-to-Many`); each ledger entry affects exactly one account (`Many-to-One`).
* **Relationship Owner:** `LedgerEntry` entity (`@JoinColumn(name = "account_id", nullable = false)`).
* **Inverse Side:** `Account.ledgerEntries` collection (`@OneToMany(mappedBy = "account")`).
* **Fetch Strategy:** `FetchType.LAZY` on `LedgerEntry`.

### 4.3. `Transaction` ⟷ `LedgerEntry` (1:N)
* **Relationship Type:** A transaction encompasses multiple ledger entries, typically debit and credit legs (`One-to-Many`).
* **Relationship Owner:** `LedgerEntry` entity (`@JoinColumn(name = "transaction_id", nullable = false)`).
* **Inverse Side:** `Transaction.ledgerEntries` collection (`@OneToMany(mappedBy = "transaction", cascade = CascadeType.ALL)`).
* **Cascade Behavior:** `CascadeType.ALL` ensures that completing a transaction atomically persists all associated `LedgerEntry` records in the same unit of work.

## 5. 🗄️ PostgreSQL DDL Schema (Physical SQL Definition)

The following SQL script outlines the schema generated by Hibernate alongside recommended **CHECK constraints** and **indexes** for institutional-grade reliability:

```sql
-- 1. Customers Table
CREATE TABLE customers (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    identity_number VARCHAR(255) NOT NULL,
    first_name VARCHAR(255) NOT NULL,
    last_name VARCHAR(255) NOT NULL,
    email VARCHAR(255) NOT NULL,
    created_at TIMESTAMPTZ,
    updated_at TIMESTAMPTZ,
    CONSTRAINT uk_customers_identity_number UNIQUE (identity_number),
    CONSTRAINT uk_customers_email UNIQUE (email)
);

-- 2. Accounts Table
CREATE TABLE accounts (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    customer_id BIGINT NOT NULL,
    account_number VARCHAR(255) NOT NULL,
    version BIGINT DEFAULT 0,
    currency VARCHAR(255) NOT NULL,
    balance NUMERIC(19, 4) NOT NULL,
    status VARCHAR(255) NOT NULL,
    CONSTRAINT uk_accounts_account_number UNIQUE (account_number),
    CONSTRAINT fk_accounts_customer FOREIGN KEY (customer_id) REFERENCES customers (id),
    CONSTRAINT chk_accounts_balance_non_negative CHECK (balance >= 0) -- Solvency invariant
);

-- 3. Transactions Table
CREATE TABLE transactions (
    id UUID PRIMARY KEY,
    idempotency_key VARCHAR(255) NOT NULL,
    type VARCHAR(255) NOT NULL,
    status VARCHAR(255) NOT NULL,
    description VARCHAR(255),
    created_at TIMESTAMPTZ,
    CONSTRAINT uk_transactions_idempotency_key UNIQUE (idempotency_key)
);

-- 4. Ledger Entries Table
CREATE TABLE ledger_entries (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    account_id BIGINT NOT NULL,
    transaction_id UUID NOT NULL,
    entry_type VARCHAR(255) NOT NULL,
    amount NUMERIC(19, 4) NOT NULL,
    created_at TIMESTAMPTZ,
    CONSTRAINT fk_ledger_entries_account FOREIGN KEY (account_id) REFERENCES accounts (id),
    CONSTRAINT fk_ledger_entries_transaction FOREIGN KEY (transaction_id) REFERENCES transactions (id),
    CONSTRAINT chk_ledger_entries_amount_positive CHECK (amount > 0) -- Ledger entry amounts must be strictly positive
);

-- ==========================================
-- Recommended Performance Indexes
-- ==========================================
CREATE INDEX idx_accounts_customer_id ON accounts(customer_id);
CREATE INDEX idx_ledger_entries_account_id ON ledger_entries(account_id);
CREATE INDEX idx_ledger_entries_transaction_id ON ledger_entries(transaction_id);
CREATE INDEX idx_ledger_entries_created_at ON ledger_entries(created_at);
```

## 6. 💡 Architectural Notes & Observations

1. **`AccountType` Enum Status:**
   * The enum `com.akt.banking_v1.enums.AccountType` (`CHECKING`, `SAVINGS`) is defined in the domain layer.
   * If checking vs. savings account distinctions are required in future iterations, this column can be integrated into the `Account` entity model.

2. **Idempotency Strategy:**
   * The `Transaction` entity enforces `unique = true` on the `idempotencyKey` column. Duplicate transfer requests are rejected at the database boundary via `DataIntegrityViolationException`.
   * If saving complete HTTP response payloads is required, a dedicated `IdempotencyRecord` table can be introduced.

3. **Concurrency and Locking Mechanics:**
   * The `@Version private Long version;` field on `Account` provides **Optimistic Locking** protection.
   * For high-frequency concurrent balance mutations, the service layer orders account IDs lexicographically to acquire **Pessimistic Write Locks** (`SELECT ... FOR UPDATE`), completely preventing deadlocks.
