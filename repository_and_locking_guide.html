🔒 2. `AccountRepository` ve Pessimistic Lock Mekanizması

Repository'ye yazdığın şu metodu hatırlayalım:

AccountRepository.java — Kilitli Okuma SQL: SELECT ... FOR UPDATE 
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("SELECT a FROM Account a WHERE a.id = :id")
Optional<Account> findByIdWithLock(@Param("id") Long id);

Bu kod veritabanında ne yapar?
Normal bir sorgu `SELECT * FROM accounts WHERE id = 1` şeklinde çalışırken, `@Lock(LockModeType.PESSIMISTIC_WRITE)` eklendiğinde PostgreSQL şu komutu çalıştırır:

SELECT * FROM accounts WHERE id = 1 FOR UPDATE;

Bu, veritabanına şunu söyler: "Bu satırı ben işlemimi bitirip COMMIT veya ROLLBACK diyene kadar KİLİTLE! Başka hiçbir transaction bu satırı değiştiremez veya kilitli okuyamaz, kuyrukta beklesin!"

📖 Gerçek Hayat Hikayesi: Ortak Hesap ve Çift Harcama (Double Spending) Felaketi

Ali ve Ayşe evlidir ve bankada ortak tek bir vadesiz hesapları vardır. Hesapta toplam 1.000 TL bakiye bulunmaktadır.

❌ Kilitsiz Sistem (Banka Batıran Senaryo)

Saat tam 14:00:00.000'da Ali Kadıköy ATM'sinden, Ayşe ise Beşiktaş ATM'sinden aynı anda 1.000 TL Çek butonuna basar.

  1. Kadıköy ATM: Bakiyeyi okur → 1.000 TL var.
  2. Beşiktaş ATM: Bakiyeyi okur → 1.000 TL var.
  3. Kadıköy ATM parayı verir (1.000 TL). Bakiyeyi 0 yapar.
  4. Beşiktaş ATM de parayı verir (1.000 TL). Bakiyeyi 0 yapar.

💥 Sonuç: 1.000 TL parayla iki ATM'den toplam 2.000 TL çekildi! Banka 1.000 TL zararda!

✅ Pessimistic Lock İle (Bizim Kodumuz)

Saat 14:00:00.000'da ikisi de butona basar:

  1. Ali'nin İşlemi: findByIdWithLock(1) çağırır. Veritabanı satırı Ali için kilitler (FOR UPDATE).
  2. Ayşe'nin İşlemi: Satıra ulaşmak ister; ama veritabanı "Dur! Satır kilitli, Ali'nin işlemi bitene kadar bekle" der.
  3. Ali parayı çeker, bakiye 0.00 TL olur ve transaction biter (Kilit kalkar).
  4. Sırası gelen Ayşe'nin işlemi içeri girer; bakiyenin 0.00 TL olduğunu görür ve "Yetersiz Bakiye" hatası döner.

🛡️ Sonuç: Tek kuruş bile kaybolmadı!

🔄 Deadlock (Ölümcül Kilitlenme) ve "Lock Ordering" Sırrı

Peki ya Ahmet ile Mehmet aynı saniyede birbirlerine para gönderirse ne olur?

  • Ahmet → Mehmet'e 100 TL atarken önce Ahmet'in hesabını kilitler, sonra Mehmet'in hesabını kilitlemeye gider.
  • Tam o anda Mehmet → Ahmet'e 100 TL atarken önce Mehmet'in hesabını kilitler, sonra Ahmet'in hesabını kilitlemeye gider.
  • DEADLOCK: İki işlem de birbirinin elindeki kilidi bırakmasını bekler ve veritabanı kilitlenir!
💡
Bizim Çözümümüz (Lock Ordering):
Servis katmanında hesapları kilitlerken gönderen veya alana göre değil; hesapların ID değerine göre (küçük ID önce) kilitleyeceğiz. İkisi de önce ID'si küçük olan hesabı kilitlemek için sıraya gireceğinden Deadlock matematiksel olarak imkansız hale gelecektir! İşte `findByIdWithLock(Long id)` metodunu bu yüzden yazdın!
📅 3. `LedgerEntryRepository` ve `DateRange` Ekstre Sorgusu

Yazdığın tarih aralığı filtreleme metodu:

LedgerEntryRepository.java — Tarih Aralığı Sorgusu JPQL BETWEEN 
@Query("SELECT le FROM LedgerEntry le WHERE le.account.id = :accountId " +
       "AND le.createdAt BETWEEN :startDate AND :endDate ORDER BY le.createdAt DESC")
List<LedgerEntry> findByAccountIdAndDateRange(
        @Param("accountId") Long accountId,
        @Param("startDate") Instant startDate,
        @Param("endDate") Instant endDate
);

Bu Metodun Önemi ve Stream API Köprüsü:

  1. Zaman Dilimi Bağımsızlığı (UTC - Instant): Tarihleri `Instant` ile tuttuğumuz için dünyanın hangi ülkesinden sorgu atılırsa atılsın saat kayması veya yaz saati farkı yaşanmaz.
  2. Performanslı İndeks Kullanımı: PostgreSQL'de `createdAt` kolonu indekslendiğinde `BETWEEN` sorguları milyonlarca satır arasından milisaniyede döner.
  3. Java Stream API ile Finansal Analitik: Bir sonraki aşamada bu metottan gelen hareketleri Java Stream API ile boru hattına sokacağız:
    • .filter(e -> e.getEntryType() == EntryType.DEBIT) → Ay boyunca yapılan toplam harcamayı bulma.
    • .map(LedgerEntry::getAmount).reduce(BigDecimal.ZERO, BigDecimal::add) → Toplam nakit giriş/çıkış ekstresini hesaplama.
